## 2. 設計の決定（理由つき）

### 楽譜の表示と速さ
- **段ごとの組版を値だけでキャッシュする**（`vfCache`、上限64段、古い順に捨てる。第1期 A・第2期 J）。
  - 理由：枠を選ぶたびに全段を VexFlow で組み直すと、Tea for Two で1回約90ms かかり、矢印キーでの移動が重かった。
  - VexFlow のオブジェクトやクロージャを持つと、64段ぶんのメモリが残る。だから中身は値と SVG の文字列だけにし、時刻→x座標は外の `vfMap` で作り直す。
- **キャッシュのキーは、その段の見た目を決めるものすべて**：曲、調、段の位置と大きさ、枠の中身、音符の色（CSS 変数）、`state.laMinor`。
  - 選択・着地点の印・再生位置はキーに入れず、`svg()` が毎回 `state` から読む。
  - 理由：色や階名は音符に焼き込まれる。一方、選択は毎回変わるので、キーに入れるとキャッシュが効かない。
- **選択だけが変わるときは、楽譜を作り直さず印を付け替える**（`selectCell`。第2期 I）。
  - ただし、楽譜がまだ出ていないとき、印を付ける枠が見つからないとき、伴奏付けで長調と短調の区間をまたぐときは、`render()` で全体を描き直す。
  - 理由：キャッシュのあとも、8段ぶんの SVG を読み直す時間が残っていた。印を付け替えるだけなら、再生位置の印も消えない。
  - 迷うときは `render()` のままにする（選択以外の変化を取りこぼさないため）。
- **確かめ方**：キャッシュあり・なしと、`selectCell` 後・`render()` 後の両方で `#sheet` が一致することを `tools/smoke.py` で見る（VexFlow が振る `vf-auto…` の id は除く）。
  - 理由：見た目の食い違いを、目で見なくても見つけられる。

### 再生
- **くり返しの次の周回は、枠の番号でなく拍の範囲から枠を探し直す**（`replayBeats`。R1）。
  - 理由：再生中に枠を結合・分割すると番号がずれ、エラーで止まった。
- **試聴（mode `"slot"`）はくり返さない**（R3）。
  - くり返すのは、全体・ここから・前小節から・聴き比べ・原曲・案。
- **メロディとコードの音量の配分は2乗で絞る**（`melGain`／`chordGain`。F）。50 で以前と同じ音量。
  - 理由：直線で絞ると、端に近づくまで変化が聞き取りにくい。

### 判定と答え合わせ
- **伴奏付けの答え合わせは、原曲と同じかどうかでなく、その場所の調での機能で比べる**（`answerNote`。E）。
  - 理由：原曲と違っても成り立つ答えは多い。
  - 根音が同じでも、ダイアトニックで同じ機能のときだけ「厚さが違うだけ」と言う。C → C7 や C → Cm は働きが違うので、そう言わない（R2）。
- **答え合わせの文は判定の文と分けて置き、狭い画面でも出す**（`.ansnote`。R4）。
  - 文が下の固定パネルに隠れるときだけ、ページを送る（`showAnsNote`、`revealAboveSheet`）。
- **狭い画面でも「機能」「度数」「転調中」は見せる**。「原曲」「次」は楽譜で見えるので隠す（K）。
  - 理由：機能と度数は学習の要。

### 学習の補助
- **用語は、文の中の語をその場で押せる形にする**（`glossed`、`GLOSS`、`TERM_TEXT`。C・R5）。
  - 1回の呼び出しで、同じ語は最初の1回だけボタンにする。候補ボタンと楽譜の中には使わない。
  - 「機能」と「T・S・D」が並ぶ文では、先に出る「機能」をボタンにする（利用者と決めた。説明の見出し「機能（T・S・D）」と合い、規則が1つで済む）。
- **階名を返す所は `solf(midi, K)` の1か所だけ**（G）。
  - 短調でラから読むかどうかは設定で切り替える（`state.laMinor`）。I・IV・V の呼び名は変えない。
- **フレーズの区切りは、曲データの任意の項目 `phrases` で決める**（H）。
  - なければ4小節ずつ。合計が小節数と合わないときは、読み込みでは黙って無視し、曲の入力では保存させない。
- **「はじめに」の案内は、閉じたら次から出さない**（`rehamo:intro`。D）。保存が使えない環境では毎回出る。

### 候補の一覧（置き換え候補・コード候補。第3期）
- **候補は同じ大きさのタイルにする**。手法ごとのグループは開閉できる。
  - 初期値は全部開く（利用者と決めた）。
  - 一番上で手法ごとに絞り込める。「ぶつかる候補を隠す」もある。
  - 理由：候補が多い枠で、全体が見渡せなかった。
- **長い説明は、一覧の上の1行に出す**。マウスでは乗せたとき、タッチ画面では長押し（450ms）で出す。長押しではコードを置かない（利用者と決めた）。
- **手法ごとの色は今のまま残し**、グループの線と絞り込みのボタンに使う（利用者と決めた）。

### 案と、コードを変える間隔（第3期）
- **1曲に案A〜案Eまで、モードごとに持つ**（`rehamo:p:`／`rehamo:hp:`）。
  - 新しい案は今の案の写しから始め、元の案が比べる相手になる。
  - 理由：リハモは何通りも試して比べるもので、1つの版を上書きすると前の版に戻れない。
  - 案ができる前に保存したコードは、最初の案として読み込む。
- **コードを変える間隔は拍子ごとに用意する**。4拍子は 1小節／2拍／1拍、3拍子は 1小節／2拍＋1拍／1拍。
  - どちらにも「骨格の音に合わせる」を用意する：1つの三和音に骨格の音が収まらない小節だけを分ける。
  - 切り替えても、その位置で鳴っていたコードを残す。
- **「逆算」タブは「着地点から」と呼ぶ**。鎖の各コードに、着地点を I とみなした度数を添える。
  - 理由：「逆算」では何をする所か分からない。

### 著作権（第3期）
- **オープンソースにせず、All rights reserved にする**（著作権者 jun、2026年）。
  - 理由：今はウェブで無料公開だが、将来は有料のアプリにする可能性がある。ライセンスはあとから緩められても、締めることはできない。
- 収める旋律は、日本と米国の両方で保護期間が終わったものだけ（`CLAUDE.md` の「曲データの決まり」）。

## 3. 項目の書き方と進め方

- 項目は「ねらい → 仕様 → 受け入れ条件」で書く。受け入れ条件は、確認担当がそのまま照らす。
- 実装は上から順に、1項目＝1コミット。
- 実装メモ・確認の結果・未決の質問は `PROGRESS.md` に書く（ここには書かない）。

## 4. 検討中：書法コア（第4期）

- ねらい：楽譜の表示・声部・和音・規則の判定を、道場シリーズの共通部品として切り出すかを決める。
- 材料：`docs/INVENTORY.md`（このアプリの中身の一覧と、共通化の候補・食い違う点）。
- 決まっていないこと（利用者が決める）：
  - 切り出すかどうか。
  - 切り出すなら何を共通にするか（INVENTORY の 7. に利用者が書く）。
  - 「C の枠で全部を持つ」設計を、共通部品の中に入れるか、このアプリに残すか。
